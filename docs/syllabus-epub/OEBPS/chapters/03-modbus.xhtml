Session 3: Speaking the Machines' Language

Goal for this session: talk directly to the water PLC over Modbus/TCP, with no HMI in the loop, and make the RO plant do things it should not. This is scenarios 4, 5, and 6. The tool is a twenty-line Python client. There is no exploit here, because Modbus does not require one.

3.1 The Plant You Are Attacking

The water side of Cross Creek is a two-pass reverse-osmosis demineralisation plant that produces ultrapure water for a downstream user, the "Mischerei." Feed water is dosed with antiscalant and pushed through RO pass 1; the permeate is dosed with a little caustic (NaOH) to knock down dissolved CO2, then polished through RO pass 2; the product goes to a DI storage tank and circulates continuously around a distribution loop with a UV steriliser on it. A control-program interlock, labelled "Freigabe an Mischerei" on the panel, only releases water to the consumer when the RO2 conductivity and the loop-return conductivity are below a limit, the UV intensity is above threshold, and the tank is not empty.

That interlock is the safety you are going to attack.

3.2 What Modbus Is, and What It Is Not

Modbus is from 1979. It is a request-response protocol over what is now TCP port 502. A client asks to read or write coils (single bits, think pump run commands) or registers (16-bit words, think setpoints and sensor values). There is no authentication. There is no session. There is no signing. If you can open port 502, you are, as far as the PLC is concerned, the HMI.

FrostyGoop, the malware that took the heat out of 600 buildings in Lviv in January 2024, was notable for being written in Go and for taking its target list from a config file. The Modbus part was not notable. It was function code 6, write single register, the same call the HMI makes every second.

3.3 Enumerate

python3 /opt/scripts/modbus_attack.py enum

That reads the coils, the discrete inputs, the holding registers, and the input registers and prints them. Match them to the panel. Coil 4 is the DI loop circulation pump 3P401. Coil 6 is the CPU keyswitch. Holding register 0 is the loop pressure setpoint (3PITC401). Holding register 5 is the conductivity limit that gates the release interlock. The full map is in plc/water-openplc/mapfile.py, but deriving the interesting registers from the panel is the exercise.

3.4 Stop the Distribution Loop (Scenario 4)

The DI loop has to circulate continuously; if it stops, the water in the loop goes stagnant and the point of use loses supply. The control program keeps the loop pump running whenever the loop sequence is active, so a bare coil write to stop it gets reasserted on the next 200 ms scan. The way around that is the same trick a real intruder uses: take the pump to HAND first, so the program stops driving it, then stop it.

python3 /opt/scripts/modbus_attack.py stop-loop
# writes coil 13 (P401 HAND) = 1, then coil 4 (P401 run) = 0

Watch 3PITC401 on the water HMI. Loop pressure bleeds from 3.8 bar toward zero in a couple of seconds, and DI_LOOP_PRESS_LOW latches. The Mischerei has lost its water, and it will hold until an operator notices the pump is in HAND and puts it back.

3.5 Defeat the Quality Gate (Scenario 5)

The dangerous attack on a water plant is not stopping a pump. It is releasing water that is not safe. The release interlock compares the measured conductivity against holding register 5. Raise that register and the gate stops meaning anything.

python3 /opt/scripts/modbus_attack.py raise-limit 5.0
# writes HR5 = 500  (5.00 uS/cm; the design limit is 2.00)

On its own that changes nothing you can see. So degrade the water underneath it. The antiscalant keeps scale off the RO membranes; cut it and they foul.

python3 /opt/scripts/modbus_attack.py starve-antiscalant
# P101 to HAND and stopped, dose rate -> 0

Watch 1QAH301. Over about thirty seconds the RO1 permeate conductivity climbs from 12 toward 50 uS/cm as the membranes scale, and then 2QAH401, the product conductivity, follows it up past 2 uS/cm. Normally that trips DI_COND_HIGH_RO2 and the interlock drops "Freigabe an Mischerei" to red, off-spec water is held. But you raised the limit to 5.0, so the alarm never fires and Freigabe stays green. The plant is now releasing demineralised water that is three times too conductive, and the panel says everything is fine.

Note the shape of that: the pure setpoint write, by itself, was harmless. The pure membrane foul, by itself, would have been caught. It took both, and it still left the release interlock's own hard limit (a program constant, not a register) as a last line. Reaching past that is Session 4.

3.6 Blind the Operator (Scenario 6)

Everything above is visible on the HMI. 2QAH401 goes red, Freigabe would normally go red, an attentive operator acts. So the mature version hides itself. The HMI reads input registers 0 through 14. The process simulator writes the real values into holding registers 10 through 22 and the PLC scan loop copies them across. If you write the mirror registers faster than the sim updates them, you control what the operator sees.

# sketch: hold RO2 conductivity and the loop values at spec on the HMI
python3 - <<'PY'
from pymodbus.client import ModbusTcpClient
import time
c = ModbusTcpClient("172.30.40.20", port=502); c.connect()
while True:
    # IR 3 = RO2 conductivity, IR 6 = DI tank, IR 7 = loop pressure, IR 9 = loop return cond
    c.write_registers(3, [55], slave=1)          # 0.55 uS/cm, looks perfect
    time.sleep(0.15)
PY

Now run the antiscalant starve from 3.5 without raising the limit. The interlock in the PLC still knows the water is bad and holds Freigabe, but the operator's screen shows 0.55 uS/cm and green, so nobody escalates, and an attacker who is also spoofing the Freigabe coil completes the picture. This is Stuxnet's operator-facing trick in miniature: record normal, replay normal, run the process off-spec behind it.

3.7 What You Should Notice

Modbus gave you the plant with no credential and no exploit, and the only thing that saved the water quality was an interlock coded into the PLC program by an engineer who thought about failure, and even that had a register you could turn off. When you get to Session 5 you will not be able to fix Modbus, because Modbus cannot be fixed. You will fix everything around it: who can reach port 502, which setpoints the program will accept, whether the release limit can be written at all, and whether anyone would see a conductivity that climbed faster than a membrane can foul.
