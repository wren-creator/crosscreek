Session 4: Vendor Dialects

Goal for this session: leave generic Modbus behind and speak the two vendor protocols that run most of the installed base, S7comm and Allen-Bradley's EtherNet/IP, and use each to do something Modbus could not: halt a CPU, operate a breaker, and replace a control program. This is scenarios 7, 8, and 9.

4.1 S7comm and the Substation RTU (Scenario 7)

STEMENS S7-300 and S7-400 controllers, and the RTUs built on that family, speak a protocol usually called S7comm, conventionally over TCP port 102, though Cross Creek's own substation RTU is not on that port either, see 2.2. Beyond reading and writing data blocks, it carries PLC-control functions: stop the CPU, start it, change its operating mode. On the older devices, and on plenty of newer ones that were never configured otherwise, none of that requires a password. Industroyer, the malware that opened breakers in Kyiv in 2016, used protocol-native commands like these.

python3 /opt/scripts/s7_attack.py read
python3 /opt/scripts/s7_attack.py trip feeder     # open breaker 52-F

Opening the feeder breaker islands the substation: it is now running on local generation alone. Watch the power HMI. With the load still connected the frequency sags; trip the load breaker too and the generation now vastly exceeds the load, and the frequency ramps upward past 50.5 Hz until the excursion alarm latches. On a real grid this is where protective relays start tripping things to save equipment, and customers go dark.

python3 /opt/scripts/s7_attack.py stop            # halt the RTU CPU

Now the RTU is in STOP. The operator still has their screen, but their commands do nothing, and the last outputs are frozen. This is the quiet version of the attack: no dramatic excursion, just a substation that no longer answers its operator.

4.2 EtherNet/IP, CIP, and the NaOH Dosing Controller (Scenario 8)

Allen-Bradley controllers speak EtherNet/IP, which carries the Common Industrial Protocol, CIP, conventionally on TCP port 44818, moved on Cross Creek's dosing controller for the same reason as the other two, see 2.2. On Cross Creek the CIP device is the controller for the RO inter-pass NaOH (caustic) dosing. Tag reads and writes are unauthenticated. If the controller keyswitch is in REMOTE, it will also accept a program download.

python3 /opt/scripts/cip_attack.py read
python3 /opt/scripts/cip_attack.py set 15         # write the DoseSetpoint tag

The tag write drives the NaOH metering rate up; the caustic overdose pushes the RO2 permeate conductivity (2QAH401) past the release limit, and just like the Modbus setpoint attack in Session 3 the release interlock catches it and holds "Release to Consumers" red. So you take the second step.

python3 /opt/scripts/cip_attack.py logic-push
# program accepted, rev 2
# metering pump forced to 100%, downstream interlock bypassed
Honest scope note. A real Studio 5000 download is not reproducible without Rockwell's tooling, so Cross Creek does not fake the wire format. The dosing controller runs an unauthenticated service that, on this request, swaps its control logic for one that pins the metering pump wide open. What is real here is the lesson: an unauthenticated program-change path on a controller in REMOTE, and the fact that it bumps a LogicRev counter that a historian could alarm on. What is a stand-in is the packet layout.

With the pushed logic running, the pump is pinned at 100 percent and the loop return conductivity climbs steadily past the limit. The release interlock is now firmly holding Release off, so the water is not being released, yet. Getting it released is the next step.

4.3 Remove the Release Interlock (Scenario 9)

The water PLC runs an OpenPLC-style runtime with a web console on port 8080, published at http://127.0.0.1:8073. Its login is openplc / openplc, which you found in notes.txt in Session 2. While the keyswitch is in REMOTE it will accept a program upload, and the uploaded program becomes the running control logic on the next scan.

python3 /opt/scripts/push_logic_water.py

The script uploads a control program that is the golden one with two changes: "Release to Consumers" is forced true regardless of conductivity or UV, and the RO2 hard-safety that stops pass 2 on grossly off-spec permeate is gone. Open the console and confirm the running program is now crosscreek_ro_v1_PATCHED. On its own nothing bad happens yet, this is a latent failure. Chain it with the CIP push from 4.2 or the antiscalant starve from Session 3 and there is nothing left in software to stop off-spec demineralised water going to the point of use.

Chain 3.5, 4.2, and 4.3 and you have the full outcome: the RO membranes fouled, the caustic dose pinned, the quality gate defeated, and the interlock deleted, with the panel still showing green if you are also blinding it.

4.4 What You Should Notice

The vendor protocols did not make you work harder than Modbus did. They gave you more: the ability to stop a CPU, operate a breaker, and rewrite the logic itself. And notice where the real danger lived in every case. It was not the setpoint write, which the interlocks caught. It was the second step, the one that removed or bypassed the safety logic. An intruder who only tampers with values gets caught by a well-written program. An intruder who can change the program is the one that ends up on the news. Session 5 starts locking that door.
